1. どんなプログラムか
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

日本の政策担当者になり、30年間、毎年「政策」を自由な文章で入力していく、ブラウザで遊ぶ政策シミュレーションゲーム。

  - モード: バブル期モード(1988年開始。「バブル崩壊を防げ!」)と現代モード(2025年開始。人口減少と技術大国の再興)
  - 社会指標67個(GDP・税収・出生率・国民満足度・内閣支持率・健康寿命・技術力・人材の過不足など)
  - プレイヤーが書いた政策を AI が評価し(どの指標に・いつ・どれだけ・一時的か恒久的か)、ゲーム側の計算(エンジン)が
    毎年の指標の値に反映する。出来事(史実・ランダム・指標が節目を越えたとき)は、AIではなく指標から計算で決める。
  - 難易度5段階、クリア条件6つ(3つは固定、3つはくじ)。30年後に満たせばクリア、破綻ラインを越えたらゲームオーバー。
  - Googleでログイン、ゲームごとのセーブデータ、記録名鑑とランキング、毎日回復する無料枠と回数の購入(Stripe)、
    秘書のキャラクターの一言とチュートリアル。

規模: Python 約12,000行(app.py と game/)。開発期間 2026-09-13〜。push は123回。

2. 使っているAI(LLM)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

■ モデル: OpenAI の gpt-5.6-luna(Responses API)
  - 推論の強さ(reasoning effort)は low。GPT-5系は推論モデルで、既定のままだと最初の出力まで長く待つため。
  - 出力は JSON Schema の構造化出力(strict)。影響の対象の指標・ピークの年・続く長さ・大きさ(0〜10)・一時的か恒久的か、
    政策の目的・手段の分類、使う人材、費用と税制、金額で決まる量(ODA・給付・防衛費)、政策の総評などを、決まった形で
    受け取る。値の範囲はコードでも確かめ、範囲の外は丸める(clamp)。
  - ストリーミングで受け取り、評価中は進み具合のバーを出す(出力の文字数から割合を出す)。ストリーミングの解析に
    失敗したときは、ストリーミングなしの呼び出しに自動で切り替える。
  - AIを呼ぶのは「政策を施行する」ときの1年1回だけ。入力の確認(政策として評価できるか)、政策への分割、影響、
    分類、総評を、1回の呼び出しでまとめて出させる。出来事・任期の総括・秘書の一言・おすすめの政策は、AIを使わない。
  - 費用: 1回0.2〜0.4円、1ゲーム(30回)で約6〜12円。プロンプトの固定部分(ルール・指標の一覧・出力の形。入力の約8割)
    の末尾にキャッシュの区切り(prompt_cache_breakpoint)を置き、モードごとのキャッシュ用の名前(prompt_cache_key)を
    付けている。実測で、2回目以降は入力の約95%がキャッシュから読まれる(その分の料金は1/10)。

■ このモデルを選んだ理由と、比べたもの(詳しくは 判断の記録/01 の1.・2.)
  1) 手元で動かすAI(ローカルLLM)をやめ、クラウドのAIにした
     - 最初の構想では、Ollama・llama-cpp-python・SGLang を比べ、モデルは Qwen・Gemma・Llama を候補にしていた
       (vLLM は NVIDIA の GPU がないため、ONNX Runtime は対応環境の制約が大きいため、最初から外した)。
     - 実際に Ollama で試作したが、開発機は独立した GPU がなく(Core i7-1165G7・メモリ16GB)、すべて CPU で推論するため、
       どのモデルも遅すぎた。27B級は量子化してもメモリに収まらない。
     - llama-cpp-python は Ollama と同じ推論エンジン(llama.cpp)なので速さはほとんど変わらず、SGLang は GPU 前提の
       設計で、この環境では利点がない。
     - クラウドのAIなら1ゲーム数円〜数十円で、速さの問題がなくなる。遊ぶ人の端末の性能にも左右されない。
  2) クラウドのAIの中から gpt-5.6-luna を選んだ
     - Claude(Sonnet・Haiku・Opus)、GPT(nano・luna・terra)、Gemini(Flash-Lite・Flash・Pro)の3社を、同じ画面で
       切り替えて、同じ政策を評価させて見比べた。
     - 値段: 格安の帯(GPT の nano・luna、Gemini の Flash-Lite)は Claude より数倍〜10倍以上安い。
     - 速さ: nano は推論で考え込み、最初の出力まで長く待つことがあった。
     - 精度: 品質の公平な比べ方がないので、実際の出力を並べて見比べ、「値段・精度・応答の速さで luna が最も理想に近い」
       と判断した。1段上の terra でも守られなかった指示(影響の件数の決まり)は、モデルを上げるのではなく、指示の書き方を
       変えて解決した。
     - いまは画面からのモデルの選択をなくした(プロンプト・難易度・費用の見積もりは、すべて luna で調整・実測したため)。
       Gemini と Claude の呼び出しのコード(同じ入出力の形)は game/ に残してあり、差し替えられる。

■ AIに任せること・任せないこと(詳しくは 評価/01_AIとゲーム側の役割分担.txt)
  AIの出力はぶれるので、AIには「政策の中身で決まる最初の一歩」だけを書かせ、それ以外はゲーム側が計算する。
    1. 指標の値だけで決まる仕組み(税収・成長率・指標どうしの連動・頭打ちなど)はゲーム側が計算する
       (AIにも書かせると二重に数える)。
    2. 政策の中身で変わる最初の一歩はAIが書く(一律の計算では、プレイヤーの工夫が結果に出ない)。
    3. 金額で決まる量(ODA・家計への給付・防衛費・一度きりの給付金・費用)は、AIに金額を書かせ、ゲーム側が換算する
       (AIの「影響の大きさ」は今の値に対する割合なので、「倍にする」「2.5兆円増やす」を正しく表せない)。
  同じ考えで、次のものもAIの直接の判断からゲーム側の計算に移した。
    - 過去の政策との相乗効果: AIには目的(16種)と手段(12種)を選ばせるだけにし、相乗・重複・矛盾はゲーム側の
      組み合わせ表で決める。AIに相乗の値を直接出させる方式(関係のない政策にもほぼ毎回プラスを付けた)、政策の文の
      ベクトル化で近さを測る方式(ぶれやすく、数百MB以上のモデルが公開先のメモリを圧迫する)と比べて選んだ(判断の記録/02 の4.)。
    - 出来事: 以前は「史実どおり起きるか・大きさ」をAIに判定させていたが、指標から計算する形にした(理由を画面に
      示せる。「耐災害指数60により被害は52%に軽減」など。判断の記録/03 の1.)。
    - 史実の趨勢(出生率・高齢化など、何もしなくても動く変化): AIには渡さず、ゲーム側が毎年足す。

4. それぞれの技術を選んだ理由(ほかの技術と比べて)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

■ Python
  ゲームの中身は、67指標の年ごとの計算・出来事の判定・難易度の調整(数千ゲームのダミープレイ)などの数値計算が中心。
  AIのライブラリ(OpenAI・Gemini・Claude)、画面(Streamlit)、決済(Stripe)のライブラリもそろっていて、画面から計算・
  調整の道具まで、1つの言語で書ける。

■ Streamlit(画面)(判断の記録/01 の5.)
  比べた案:
    A. Streamlit のまま、配色・CSS・レイアウトで見た目を整える
    B. 画面だけ React などで作り直し、Python のゲームの計算を裏側のサーバーで動かす
  選んだ理由:
    - B は自由度が高いが、作業量が大きく(目安15〜30時間、Node.js の導入)、公開するときに裏側の Python のサーバーも
      別に要る(無料の枠は眠りやすく、常に動かすなら月800〜1,100円ほど)。
    - Streamlit なら、Python だけで画面とゲームの計算を一緒に書け、Streamlit Community Cloud で無料で公開できる。
  Streamlit の弱いところは、工夫で補った。
    - ボタンを押すたびにサーバーで画面全体を描き直すので、チュートリアルの「次へ」に1秒ほどかかった。段階の切り替えは
      画面の側の JavaScript だけで行い、サーバーが要るときだけ隠したボタンを押すようにした(push履歴 117)。
    - st.markdown は svg のタグを取り除くので、グラフは components.html に入れた。以前は Altair のグラフだったが、
      「政策なしの線から実際の線へ動く」見せ方のために、SVG のアニメーション(JavaScript なし)に替えた(判断の記録/04 の6.)。
    - Webhook(外からの通知)を受ける口を作れないので、決済の確認は問い合わせの形にした(下の Stripe を参照)。
    - 開いているあいだにプログラムが更新されてエラーの画面になったら、画面の側で見つけてページを読み込み直す(push履歴 120)。

■ 公開先: Streamlit Community Cloud(判断の記録/05 の6.)
  比べた案: A. Streamlit Community Cloud+無料のクラウドのデータベース(0円から。使われないと眠る・メモリが小さい) /
            B. Render・Railway などのサーバー+データベース(月数百〜千円ほど。眠らず安定)
  選んだ理由: まず無料の A で公開して確かめ、利用者が増えたら B に移す。

■ データベース: 手元は SQLite、公開先は Neon(PostgreSQL)(判断の記録/01 の7.、05 の7.・7-2.)
  - 公開先では、手元のファイルは再起動で消えることがあるので、購入の記録などを置くにはクラウドのデータベースが要る。
  - Supabase と Neon を比べた。Supabase の無料の枠は1週間使われないと止まり、手で戻す必要がある。Neon は使われないと
    計算部分が休むが、接続すれば自動で起きる。地域は、公開先のサーバーに近い AWS US East にした。
  - 手元(日本)からアメリカの Neon へは1回の読み書きに約0.7秒かかり、手元の確認で本物の記録を書き換える危険もあるので、
    手元は SQLite にした。同じ関数・同じ SQL のまま、設定(APP_DB_PATH / DATABASE_URL)で切り替える。

■ ログイン: Streamlit の st.login(Google)(判断の記録/01 の6.)
  比べた案: st.login で Google のログイン / メールアドレスでも登録できるようにする(Auth0 などの外部サービスが要る) /
            自前でパスワードを預かる
  選んだ理由: st.login は標準の機能で、一番早く安全。自前でパスワードを預かると、漏れたときの危険と、パスワードの
              再設定の仕組みを作る手間が出る。このアプリはパスワードを一切扱わない。

■ 決済: Stripe Checkout の買い切り、Webhook なし(判断の記録/05 の2.・4.)
  - 回数パックの買い切りと、月額のサブスクを比べた。サブスクは「支払い完了」「解約」などの通知(Webhook)を受ける口が要るが、
    Streamlit では作れず、別にクラウドの関数などを用意することになる。買い切りなら、アプリから Stripe に「支払いは
    済んだか」を問い合わせるだけで済み、早く安全に作れる(毎日30回パスも、自動更新のない買い切りにした)。
  - 支払いの確認は、支払いを終えて戻ってきたとき・ログインした画面を開いたとき・支払いページを作ったタブで10秒ごと
    (Streamlit の fragment)に行う。「確認待ち」の行を「支払い済み」に変えられたときだけ回数を足すので、二重には足さない。
  - 決済のサービスは Stripe 以外と比べていない(日本でカード・Apple Pay・Google Pay が使え、月額の固定費がないことを
    確かめて、そのまま進めた)。

■ AIのAPIの料金を開発者が払う(判断の記録/01 の4.、05 の13.)
  遊ぶ人に自分のAPIキーを入れてもらう形は、一般の人がキーを持っていないので、開発者のキーで払い、利用に上限を付けた。
  政策の施行はログインが必要で、無料枠は最大5回(ログインした日ごとに2回分回復)、それ以上は購入した回数を使う。
  悪用で請求が青天井にならないよう、OpenAI 側の月の予算も組み合わせる。

■ コードは非公開、設計資料だけを公開(判断の記録/01 の3.)
  GitHub には「リンクを知っている人だけ見られる」設定がないので、コードのリポジトリは非公開にし、設計資料だけをこの
  公開リポジトリに置いた(就職活動の提出物としてURLを渡せ、コードは守れる)。

      +-- game/summary.py, charts.py  任期の総括・動く推移のグラフ
      +-- game/policy_ideas.py        指標ごとの政策案・おすすめの政策
      +-- game/ui_theme.py            見た目(CSS)・秘書の絵
      +-- game/tutorial_js.py         チュートリアル(画面の側で動く JavaScript)

  サーバーがつなぐ外部のサービス
      - OpenAI API      政策の評価(1年1回)
      - データベース    公開先は Neon(PostgreSQL)、手元は SQLite
      - Stripe          決済
      - Google          ログイン

  - 画面(app.py)とゲームの計算(game/)を分けている。game/ の計算は Streamlit に依存しないので、難易度の調整の道具
    (tools/calibration)からも同じ計算を使い、AIを呼ばずに数千ゲームを進められる。
  - AIの呼び出しは、3社とも同じ入出力の形(stream_policy_evaluation など)にそろえ、結果は共通の型(AIResult・
    StreamUpdate)で受け取る。JSON Schema は3社の構造化出力のどれでも通る書き方にそろえた。
  - ゲームの状態(GameState)は、指標の値・進行中の効果(政策や出来事ごとの山)・出来事の記録・報告書を持ち、毎回の
    操作のあとにデータベースへ保存する。乱数の種もゲームごとに保存するので、同じ種なら同じ出来事が起きる。

6. 動作の流れ
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

■ 6-1. ページを開いたとき
  1. 秘密の設定を読む(APIキー・データベース・Stripe の鍵など。コードには書かない)。
  2. 利用者を決める。ログインしていれば Google のアカウント、していなければ接続元から作った記号(IPアドレスそのものは
     保存しない)。ログインしていて、その日(日本時間)初めてなら、無料枠を回復する(ログインボーナス)。
  3. 保存してあるゲームがあれば、続きから再開する。別のタブで同じゲームが進んでいたら、新しい方を読み込む
     (保存のたびに番号を進め、知っている番号と同じときだけ書く)。
  4. 初めて遊ぶ人には、秘書のチュートリアルを出す。

■ 6-2. 政策を施行したとき(1年進む)
  1. 回数を確かめる(ログインしているか・無料枠か購入した回数が残っているか)。
  2. AIへの入力を組み立てる。
       固定部分: ルール・67指標の一覧・出力の形・モードの舞台設定(「当時の経済規模に対する比率で評価する」
                 「後知恵で判断しない」など)。キャッシュが効くよう、毎回同じ文にする。
       状況:     指標の今の値と開始時・前年からの変化、これまでの政策、進行中の効果(上位8件)、直近2年の出来事。
       入力:     プレイヤーの政策(100文字まで)。
  3. AI(gpt-5.6-luna)をストリーミングで呼び、進み具合のバーを出す。返ってきた JSON を確かめる。
       - 入力の確認: 政策 / 読み替えた政策(実行できない前提を除いた形で評価) / 政策として評価できない(年を進めない)
       - 1回の入力を1〜5件の政策に分け、それぞれの目的・手段・使う人材・費用と税制・金額で決まる量を書く
       - 良い影響・悪い影響(件数は分けた政策の数に応じて上限が変わる)と、政策の総評(5種類から1つ)
  4. 使った回数を数える(無料枠を先に使い、なくなったら購入した回数)。戻りの時計のために、施行の直前の状態を残す。
  5. ゲーム側が影響を登録する(simulation.add_policy_effects)。
       - 影響ごとに、正規分布の山(ピークの年・ばらつき・一時的か恒久的か・大きさの2乗の倍率)を作る
       - 過去の政策との相乗・混乱(組み合わせ表)、人材の不足による遅れ・効果の低下、限界に近い指標の頭打ちをかける
       - 費用・税率の変更・金額で決まる量は、山ではなく固定の値としてゲーム側が計算する
  6. その年の出来事を決める(resolve_events)。バブル期は史実の出来事、現代モードは候補からの抽選。起きるか・
     避けられるか・大きさは、指標(政策なしで進んだ場合との差など)で決まる。
  7. 1年進める(advance_year)。
       - 進行中のすべての効果の、その年の分を足し、史実の趨勢(人口・出生率など)を足す
       - 指標どうしの連動(例: 可処分所得 → 出生率・婚姻率)、人材の過不足の構造的な変化
       - 潜在成長率(働き手・企業収益・技術力・デジタル化・研究開発費・不良債権から計算)と、景気の山谷、地価・不良債権
       - 財政: 税目ごとの税収(負担率×課税ベース)、毎年の継続出費、利払い、フリーキャッシュと国の債務残高
       - 指標が節目を越えたときの出来事(記念・隠しイベントを含む194件)を判定する
       - 破綻ラインを越えていればゲームオーバー、30年目ならクリア条件を判定する
  8. 保存する。30年を終えたゲームは、記録名鑑・ランキングに記録する。
  9. 画面: まず年が進むときの画面(「1990 → 1991」、政策の総評、その年の出来事)を出し、「報告書を読む」で、審議官の
     報告書(政策ごとの影響・相乗効果の理由・その年の出来事)と更新された指標に進む。秘書が、いちばん大事なことを
     1つ吹き出しで言う(AIは使わない)。

■ 6-3. 購入するとき
  1. 「購入する」で Stripe に支払いページを作り、データベースに「確認待ち」として記録する(1人1時間に5つまで)。
  2. 支払いページは新しいタブで開く(公開先ではアプリが枠(iframe)の中で動き、Stripe のページは枠の中での表示を拒むため)。
  3. 支払いを終えて戻ってきたとき・開き直したとき・元のタブで10秒ごとに、Stripe に支払い済みかを問い合わせ、
     「確認待ち」を「支払い済み」に変えられたときだけ、回数・パス・戻りの時計を足す。

■ 6-4. ゲームが終わったとき
  クリア・目標未達・ゲームオーバーの演出の画面(CSS のアニメーション)のあと、任期の総括(政策なしで進んだ場合より
  良くなった・悪くなった指標、国家目標の推移の動くグラフ)を出す。総括もAIを使わず、指標の推移から作る。

7. 品質・費用・安全のための工夫
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  - 評価のぶれを減らす: 大きさ1以上の影響は上限まですべて書かせる(弱い影響のどれを先に思いついたかで結果が大きく
    変わっていたため)。分けた政策1件の中で、同じ指標に良い影響と悪い影響の両方があれば、差し引いて1つにする。
  - 難易度の調整: 実際のAIで評価した政策を保存し、それを使い回すダミープレイを、クリア条件の組み合わせ264通りのそれぞれで
    行い、どの組み合わせでも同じ難易度なら同じくらいのクリア率になるよう目標を決めた(APIを呼ばないので費用0)。
  - 確認はAIを呼ばずに行う: 確認用のサーバーでは、AIの代わりに保存した評価を返すダミーのサーバーにつなぐ。
    本物のAIを使った確認は、そのたびに許可を取って最小の回数だけ行った。
  - 料金の上限: 無料枠と購入した回数、1人1時間の支払いページの数の制限、AIの月の予算。
  - 個人情報: AIには政策の文とゲームの状況だけを送り、アカウントの情報は送らない。パスワードは扱わない。
    ランキングはニックネームで表示し、Google の名前・メールアドレスは見せない。利用者は設定の画面から、自分の記録と
    アカウントを消せる。
  - 秘密の値(APIキー・データベースの接続・Stripe の鍵)はコードにもリポジトリにも入れず、設定から読む。
  - 遊ぶ人には、AIの生のデータ・トークン数・詳しいエラー文を見せない(開発者モードだけで出す)。使っているAIの
    サービス・モデルの名前は、画面には出さない(開発者モードでも)。
