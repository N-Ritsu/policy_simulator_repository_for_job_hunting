05 課金と公開
===============================================

■ 1. 無料で遊べる量(2026-09-21、10-17)
【決めたこと】 ログインしていなければ5回、ログインすれば合計15回まで無料で評価できる。それ以降は購入した回数を使う。
【比べた案】 当初(2026-09-21)のユーザーの考えは「1人あたりゲーム1回かつ15年まで無料、それ以降は課金(最小100円〜)」。
            ログインを入れるとき(2026-10-17)に、評価の回数で数える今の形にした。
【決め手】 ログインを入れたことで、回数をアカウントごとに数えられるようになった。ログインし直して無料枠を増やせない
          よう、ログイン前に使った回数の引き継ぎは1回だけにした。
【決めた人】 ユーザー。
【変更履歴】 68(103 で「ログイン必須・無料枠は最大5回で毎日2回分回復」に変えた。13 を参照)

■ 2. 課金は「回数パックの買い切り」から始める(2026-10-16〜17)
【比べた案】 - 回数パックの買い切り(目安4〜6時間) / - 月額のサブスク(目安8〜12時間)
【決め手】 サブスクでは、Stripe から「支払い完了」「解約」などの通知(Webhook)を受け取る必要があるが、Streamlit では
          その受け口を作れず、別にクラウドの関数などを用意することになる。買い切りなら、アプリから Stripe に「支払いは
          済んだか」を問い合わせるだけで済み、早く安全に作れる。反応を見てからサブスクを検討する。
          決済のサービスは、Stripe 以外とは比べていない(Claude が最初から Stripe で説明し、そのまま進めた。説明では、
          日本でカード・Apple Pay・Google Pay・コンビニ払いなどが使え、月額の固定費がないことを伝えた)。
【決めた人】 ユーザー。
【変更履歴】 81

■ 3. 値段(2026-10-17)
【決めたこと】 評価 100回 100円 / 350回 300円 / 1500回 980円、戻りの時計 10個 50円(税込み・使用期限なし)。
【比べた案】
  - Claude の叩き台: 30回(1ゲーム分)250円、150回(5ゲーム分)980円、時計3個120円
  - ユーザーの案: 100回100円、350回300円、1500回980円、時計50個80円
【決め手】 AIの費用(1回0.2〜0.4円)と Stripe の手数料(カード3.6%)を引いても、どのパックも利益が残る。1500回パックが
          いちばん利益の幅が薄い(35〜66%)が、50ゲーム分なので使い切らない人が多い。時計50個は、30年のゲームでほぼ毎年
          やり直せる量だ、と伝えたところ、ユーザーが10個50円に変えた。
          少額の決済はカードの不正な試し打ちに狙われやすく、チャージバック1件で約1,500円の手数料がかかることがあるため、
          購入はログイン必須、1人が1時間に作れる支払いページは5つまでにした。
【決めた人】 ユーザー。
【変更履歴】 81(103 で値段を変えた。13 を参照)

■ 4. 支払いの確認は Webhook を使わず、戻ってきたときと開き直したときに問い合わせる(2026-10-17)
【決めたこと】 「購入する」で Stripe の支払いページを作り「確認待ち」として記録する。支払いを終えて戻ってきたときと、
              ログインした画面を開いたとき(1回)に Stripe に問い合わせ、支払い済みなら回数・時計を足す。確認待ちの行を
              「支払い済み」に変えられたときだけ足すので、二重には足さない。
【決め手】 2. のとおり Streamlit では Webhook を受けられない。途中でページを閉じても、開き直したときに確かめ直すので
          取りこぼさない。
【変更履歴】 81

■ 4-2. 支払いページは新しいタブで開く(2026-10-19)
【比べた案】 - 同じタブ(枠の中)で開く(81。手元では動いた) / - 枠の外のページごと移す(_top) / - 新しいタブで開く(_blank)
【決め手】 公開先(Streamlit Community Cloud)では、アプリが外側のページの中の枠(iframe)で動く。枠の中で開くと、Stripe の
          支払いページは安全のため他のサイトの枠の中での表示を拒み、白い画面で止まった(ユーザーの報告)。枠の設定(sandbox)は
          新しいタブ(allow-popups)を許し、外側のページを移すこと(allow-top-navigation)は許していないので、新しいタブにした。
          戻り先のURLも、枠の印(/~/+)を除いた外側のページのURLにした。
【決めた人】 Claude(公開先の枠の設定を調べて決めた)。
【変更履歴】 94

■ 4-3. 支払いページを作ったタブでも、支払いを自動で反映する(2026-10-19)
【比べた案】 - 開き直したときだけ確かめる(それまで。元のタブは読み込み直すまで回数が増えて見えない) /
            - 画面を操作するたびに確かめる / - 10秒ごとに、画面の一部(fragment)だけで確かめる
【決め手】 ユーザーは、確かめる処理で読み込みが遅くならないかを気にした。Stripe への問い合わせは1回0.2〜0.5秒ほど。画面全体の
          描き直しのたびに問い合わせると、そのぶん表示が遅れる。Streamlit の fragment の10秒ごとの描き直しのときだけ
          問い合わせれば、画面の表示は遅くならず、操作しなくても10秒ほどで反映される。問い合わせるのは、そのタブで
          支払いページを作ってから、支払いが済むか期限切れになるまでの間だけ。
【決めた人】 ユーザー(「それで入れてください」)。
【変更履歴】 95

■ 5. 支払い方法は、Stripe のダッシュボードで選ぶ(2026-10-17)
【決めたこと】 支払い方法(カード・Apple Pay・Google Pay など)はコードで指定せず、ダッシュボードの設定で選ぶ。少額の
              パックがあるので、コンビニ払いは切っておくことを勧めた。
【決め手】 最初はカードだけをコードで指定したが、今の Stripe の API では指定できなくなっていた(payment_method_types が
          使えない)。コンビニ払いは少額だと手数料の割合が重くなる場合がある。
【変更履歴】 81

■ 6. 公開先は Streamlit Community Cloud(無料)(2026-10-17)
【比べた案】
  A. Streamlit Community Cloud+無料のクラウドのデータベース(0円から。使われないと眠る、メモリが小さい、商用での
     利用の扱いは利用規約の確認が必要)
  B. Render・Railway などのサーバー+データベース(月数百〜千円ほど。眠らず安定)
【決め手】 Claude は「まずAで公開して確かめ、利用者が増えたらBに移す」を勧め、ユーザーが無料のAを選んだ。
【決めた人】 ユーザー。
【変更履歴】 82

■ 7. データベースは Neon(無料の PostgreSQL)(2026-10-17)
【比べた案】 Supabase / Neon
【決め手】 Supabase の無料の枠は、1週間使われないと止まり、手で戻す必要がある。Neon は使われないと計算部分が休むが、
          接続すれば自動で起きる。地域は、Streamlit Community Cloud のサーバーがアメリカにあるので、近い AWS US East に
          した。接続は Neon の接続の中継(Connection pooling)を使わない直接の接続にし、アプリ側で接続を使い回す
          (中継があるとサーバー側の prepared statement が問題になることがあるため、使わない設定にもした)。
          確認用のサーバーは APP_DB_PATH で SQLite に固定し、公開先のデータベースを触らないようにした。
          (84で追記)実際にユーザーが置いた接続の文字列は、接続の中継(-pooler)を通るものだった。アプリはサーバー側の
          prepared statement を使わない設定にしてあるので、中継を通っても全部の確認が通り、そのまま使うことにした。
          手元は SQLite のままにした(下の 7-2.)。
【決めた人】 提案をユーザーが了承した。
【変更履歴】 82, 84

■ 7-2. 手元で動かすときは SQLite、公開先だけ Neon(2026-10-18)
【比べた案】 - 手元でも Neon を使う(secrets.toml の DATABASE_URL をそのまま使う) / - 手元は SQLite(.env の APP_DB_PATH)
【決め手】 手元(日本)からアメリカの Neon へは、1回の読み書きに約0.7秒かかり、1回の画面の表示で何度も読み書きするので
          遅くなる。公開したあとに、手元の確認で公開先の本物の記録を書き換えてしまう危険もある。公開先(Streamlit
          Community Cloud)はアメリカにあるので、Neon との間は速い。
【決めた人】 Claude(ユーザーへの報告で説明)。
【変更履歴】 84

■ 8. 特定商取引法に基づく表記は「請求があれば遅滞なく開示」(2026-10-17)
【決めたこと】 販売事業者・運営責任者・所在地・電話番号は「請求があった場合には、遅滞なく開示いたします。」とし、
              問い合わせ先のメールアドレスは常に載せる(このサービス専用のアドレスを勧めた。コードには書かず、秘密の設定
              CONTACT_EMAIL から読む)。
【比べた案】 - 名前・住所・電話番号をそのまま載せる / - 「請求があれば遅滞なく開示」とする / - バーチャルオフィスの
            住所・電話番号を載せる
【決め手】 ユーザーは個人名が公開されることを心配していた。「請求があれば開示」なら常には出さずに済む(ただし請求されたら
          教える義務がある)。法律の専門家の確認ではないので、消費者庁の特定商取引法ガイドで条件を確かめることを勧めた。
          Stripe が審査で個人名の省略を認めるかは、確かな情報が見つからなかった。
【決めた人】 ユーザー。
【変更履歴】 82

■ 9. 課金を完成させてから、みんなに知らせる(2026-10-17)
【決めたこと】 アプリを公開先に置く(URLは知らせない)→公開先でテストモードの課金を確かめる→特定商取引法に基づく表記などを
              載せる→Stripe の本番の審査→本番の鍵に替えて自分で100円を買う→ここで初めて知らせる、の順。
【決め手】 ユーザーは課金が完成してから公開したい。Stripe の審査ではサイトを見られる必要があるので、置くことだけは先に要る。
【決めた人】 ユーザー。
【変更履歴】 82

■ 10. プライバシーポリシーでは、AIのサービスの名前を出さない(2026-10-17)
【決めたこと】 外部に送る先として、ログイン(Google)・決済(Stripe)・サーバー(Streamlit Community Cloud)・データベース
              (Neon)は名前を書き、AIは「外部のAIサービス」と書く。AIには政策の文とゲームの状況だけを送り、アカウントの
              情報は送らないことを書く。
【決め手】 プロバイダー・モデルの名前を画面に出さない方針(64)に合わせた。AIに送るのは政策の文とゲームの状況だけで、
          アカウントには結び付かない。
【決めた人】 Claude が下書きで決めた(ユーザーの確認待ち)。
【変更履歴】 82

■ 11. 開示・訂正・削除は、できるだけ利用者が画面で自分でできるようにする(2026-10-18)
【決めたこと】 設定の画面に「記録の削除」と「アカウントの削除」を足し、プライバシーポリシーの6.を「画面で自分でできること」
              と「それ以外はメールで請求」に書き直した。アカウントを消しても、使った回数と購入の記録は残す。
【比べた案】
  - 開示・訂正・削除は、すべてメールの請求で受ける(82の下書き)
  - 画面で自分でできるようにし、残りをメールで受ける
  - アカウントの削除で、使った回数・購入の記録も含めて全部消す / 一部を残す
【決め手】
  - ユーザーの疑問「情報の公開状況を、サイト上でユーザー側が訂正できないのか」から。もともとニックネームの変更・ランキング
    の取りやめ・セーブデータの削除は画面でできたので、足りない記録とアカウントの削除を足せば、メールでの請求はほとんど
    要らなくなる。
  - 使った回数を消すと、消してログインし直すだけで無料の回数(15回)が戻ってしまう。
  - 購入の記録は、売上の記録として確定申告のために一定期間残す必要がある。ただし、買った回数としては数えない(閉じる)。
    そのため、使っていない買った回数と時計は、アカウントと一緒になくなる(削除の前に表示する)。
【決めた人】 ユーザー(「それでお願いします」)。
【変更履歴】 85

■ 12. Stripe を本番にする前に、テストのときの決済を片づける(2026-10-23)
【決めたこと】 鍵(sk_test_ / sk_live_)と違うモードの確認待ちの決済(cs_test_ / cs_live_)は、Stripe に問い合わせずに
              期限切れにする。手元はテストの鍵のまま、公開先だけ本番の鍵にする。
【比べた案】 - コードで、モードの違う決済を期限切れにする / - 本番に切り替える前に、データベースの確認待ちの行を手で消す /
            - 何もしない
【決め手】 何もしないと、テストのときに払わずに閉じた決済が「確認待ち」のまま残り、本番の鍵では問い合わせに失敗し続けて、
          その人がログインするたびに「支払いを確認できませんでした」と出る。手で消すのは、公開先の Neon を直接いじる
          ことになり、消し忘れや消しすぎのおそれがある。コードなら、あとでテストに戻したときも同じように動く。
          期限切れにした決済も、あとで支払い済みが分かれば反映できる(支払い済みにできるのは、確認待ちか期限切れの行)。
【決めた人】 Claude(ユーザーの「Stripe の本番化をしたい」を受けて)。
【変更履歴】 99

■ 13. ログイン必須・無料枠の毎日回復・新しい値段と毎日30回パス(2026-10-25)
【決めたこと】
  - 1回目の政策からログインが必要。無料枠は最大5回で、ログインした日(日本時間)ごとに2回分回復する。来なかった日の分は
    貯まらない。施行すると無料枠を先に使い、なくなったら購入した回数を使う。
  - 値段: 政策 30回 100円 / 100回 300円 / 毎日30回パス 980円 / 戻りの時計 10個 50円(据え置き)。
  - 毎日30回パス: 買い切り。購入から30日間、ログインした日ごとに無料枠が30回まで回復する(上限も30回)。買ったその場で
    30回まで回復する。もう一度買うと、残りの期間に30日を足す。31日目からはふつう(毎日2回・最大5回)に戻り、残った
    無料枠は減らさない。
【比べた案】
  - パス: 30日間、毎日30回まで回復(おすすめ) / 30日間、毎日+30回が貯まる(上限なし) / 毎月自動更新のサブスク
  - ボーナス: その日に開いた日だけ(おすすめ) / 来なかった日の分も貯まる(上限5回)
  - 以前から使っていた人の数え直し: 無料枠を5回にし、使った回数のうち以前の無料の15回を超えた分を、購入した回数から
    使ったものとする / 以前の残りの無料の回数をそのまま無料枠にする
【決め手】
  - 個人制作のゲームを置くサイトで遊んだ人の修正案を、ユーザーがそのまま依頼した(ログイン必須・無料枠5回・毎日2回分・
    無料枠を優先、100円30回・300円100回・980円で1か月毎日30回)。細部はユーザーに聞き、パスは「30日間、毎日30回まで
    回復」、ボーナスは「その日に開いた日だけ」を選んでもらった。
  - サブスクは、解約や支払い失敗の知らせ(Webhook)を受け取る仕組みが要る(2 と同じ理由)ので、買い切りのパスにした。
  - 以前の無料の15回の残りをそのまま無料枠にすると、上限5回を超える人が出て、新しい決まりと食い違う。購入した回数は、
    以前の数え方で「無料の15回を超えて使った分」だけ使ったことにすれば、買った人が損をしない。
  - AIの費用(1回0.2〜0.4円)に対して、30回100円は1回約3.3円なので、どのパックも利益が残る。パスを毎日30回使い切っても
    30日で900回(費用は約180〜360円)で、980円を下回る。
  - アカウントを消すと、購入した回数とパスはなくなる(購入の記録は閉じる)ので、購入した回数のうち使った回数も0に戻す
    (あとで買い直したときに、前の分で減らないように)。無料枠の残りは、消して取り直せないよう残す。
  - 同じ日に2つの画面を同時に開いても、ボーナスを2回受け取らないよう、日付が変わっていないときだけ書き換える。
【決めた人】 ユーザー(決まりと値段、パス・ボーナスの細部)。以前から使っていた人の数え直しと、削除のときの扱いはClaude。
【変更履歴】 103

■ 14. 開いているあいだにプログラムが更新されて、エラーの画面になったら、ページを読み込み直す(2026-10-26)
【決めたこと】
  - エラーの画面(Streamlit の stException)が出たら、1.5秒待って、まだ出ていればページを読み込み直す。読み込み直す
    あいだは「画面を新しくしています…」と出す。直前(60秒以内)に読み込み直したのにまた出たときは、繰り返さずに
    エラーの画面のままにする。
【比べた案】
  - エラーの原因を1つずつなくす / Python の側で全体を try で囲んで、エラーのときに読み込み直させる /
    画面の側でエラーの画面を見張り、出たら読み込み直す
【決め手】
  - 公開先は、push するとその場でプログラムを入れ替え、開いている画面は次の操作で新しいプログラムを動かす。そのとき、
    更新の途中のファイルを読んだり、前のプログラムで作った状態が合わなかったりしてエラーになりうる。原因が更新の
    タイミングなので、1つずつなくすことはできない。
  - Python の側で囲むには、app.py 全体を関数にする大きな作り替えが要る。それに、import の途中のエラーは囲めない。
    画面の側で見張れば、どこで起きたエラーでも同じように扱える。
  - 読み込み直しても、ゲームは保存したところから再開する(ログインしていない人も接続元で、ログインした人はアカウントで
    保存している)。失うのは、入力欄に書きかけの文字くらい。
  - 本当の不具合でエラーが出るときに、読み込み直しを繰り返さないよう、60秒に1回までにした。
  - 見張りは、iframe からページの側に差し込んで動かす(iframe がなくなっても見張りが続くように。117と同じ)。ページを
    開いた最初の表示からエラーになるときは、見張りを差し込む前に止まるので働かない(このときは読み込み直しても同じ)。
【決めた人】 ユーザー(エラーが出たら読み込み直したい)。待つ時間・繰り返さない決まり・見張りの作り方はClaude。
【変更履歴】 120
