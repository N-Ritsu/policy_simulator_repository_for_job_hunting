01 技術と開発の進め方
===============================================

■ 1. AIを手元(ローカル)で動かすのをやめ、クラウドのAIにした(2026-09-16〜19)
【決めたこと】 Ollama などで手元のモデルを動かす方式をやめ、クラウドのAI(API)で政策を評価する。
【比べた案】
  - Ollama で軽いモデル(3B〜7B、量子化 q4)を使う
  - llama-cpp-python に乗り換える
  - SGLang に乗り換える
  - クラウドのAI(Claude・GPT・Gemini)
【決め手】
  - 開発機は独立したGPUがなく(Core i7-1165G7・統合GPU・メモリ16GB)、すべてCPUで推論するため、どのモデルも遅すぎた。
    27B級は量子化してもメモリに収まらず、スワップで破綻する。
  - llama-cpp-python は、Ollama の中で使われている llama.cpp と同じ推論エンジンなので、速さはほとんど変わらない
    (HTTPの層の分、1〜2割程度)。
  - SGLang は GPU 前提の設計で、この環境では利点がなく、むしろ遅くなるおそれがある(当初の技術スタックの資料で
    vLLM を GPU がないため外したのと同じ理由)。
  - クラウドのAIなら、1ゲームの費用は数円〜数十円で、速さの問題がなくなる。
【決めた人】 ユーザー(「ローカルLLMはもう使わない」)。
【変更履歴】 01, 02

■ 2. 評価に使うモデルを gpt-5.6-luna にした(2026-09-16〜21)
【決めたこと】 OpenAI の gpt-5.6-luna を使い、プロバイダー・モデルの選択欄は消す。
【比べた案】 Claude(Sonnet・Haiku・Opus)、GPT(nano・luna・terra など)、Gemini(Flash-Lite・Flash・Pro)。
            3社を同じ画面で切り替えて見比べられるようにして試した。
【決め手】
  - 価格は、格安の帯(GPT の nano・luna、Gemini の Flash-Lite)が Claude より数倍〜10倍以上安い。1ゲームの差は
    数十円以内。
  - 品質は公平な比べ方がないため、同じ政策を実際に並べて見比べることにした(Claude 側が「Claude が一番」と言うと
    偏りがあることも伝えた)。
  - 実際に試して、ユーザーが「値段・精度・応答の速さで luna が最も理想に近い」と判断した。nano は推論で考え込み、
    最初の出力が出るまで長く待つことがあった。
  - 「luna より上のモデルにすべきか」も確かめたが、守られなかった指示(影響の件数を5件まで増やす規則)は、
    指示の書き方を変えて解決した。
【決めた人】 ユーザー。
【変更履歴】 02, 03, 07

■ 3. コードは非公開、設計資料だけを別の公開リポジトリに置く(2026-09-21)
【決めたこと】 コードのリポジトリ(policy_simulator)を非公開にし、設計資料だけの公開リポジトリ
              (policy_simulator_repository_for_job_hunting)を作る。push履歴も公開側に入れる。
【比べた案】
  A. 今のリポジトリを非公開にする(就活では相手を個別に招待する)
  B. 非公開にし、設計資料だけの公開リポジトリを作る
  C. 履歴からコードを消して、設計資料だけを残す
【決め手】
  - GitHub には「リンクを知っている人だけ見られる」設定がない。
  - B なら、就活の提出物としてURLを貼れて、コードは守れる。
  - C は、履歴を書き換えても GitHub に古いコミットがしばらく残ることがあり、一度公開した事実も消えないので勧めなかった。
【決めた人】 ユーザー(B を選んだ)。
【変更履歴】 06

■ 4. AIの料金は開発者のキーで払い、利用に上限を付ける(2026-09-21)
【決めたこと】 遊ぶ人にAPIキーを入れてもらうのではなく、開発者のキーで払い、無料で遊べる量に上限を付けて、
              それ以上は課金にする。
【比べた案】
  - 遊ぶ人自身のキーを入れてもらう(開発者の費用はかからないが、一般の人はキーを持っていない)
  - 開発者のキー+利用の上限(自動チャージ・月の予算・1人あたりの回数の上限を組み合わせる)
  - 安いモデルを既定にする
【決め手】 一般向けに公開するなら、開発者のキー+上限しか現実的でない。自分のキーで全員の分を払うと、悪用されたときに
          請求が青天井になるので、月の予算と回数の上限を必ず組み合わせる。
【決めた人】 ユーザー。
【変更履歴】 07(無料枠の具体的な回数は 05_課金と公開 を参照)

■ 5. 画面は Streamlit のまま作り直す(2026-10-16)
【決めたこと】 画面の刷新は Streamlit のまま、配色・CSS・レイアウトで行う。
【比べた案】
  1. Streamlit のまま見た目を整える
  2. 画面だけ React などで作り直し、Python のゲームの計算を裏で動かす(作業の目安15〜30時間、Node.js の導入、
     公開には裏側のサーバーが別に要る)
【決め手】
  - 2 は自由度が高いが、作業量が大きく、公開するときに裏側の Python のサーバーも別に用意する必要がある
    (無料の枠は眠りやすく、常に動かすなら月800〜1,100円ほど)。
  - Streamlit 版なら Streamlit Community Cloud で無料で公開できる。
【決めた人】 ユーザー(「サーバー無料でできるなら、一旦Streamlit版で」)。
【変更履歴】 65

■ 6. ログインは Streamlit の st.login(Google)にした(2026-10-16)
【決めたこと】 Google アカウントでのログインだけにする。パスワードはアプリで預からない。
【比べた案】
  - Streamlit の st.login で Google のログイン
  - メールアドレスでも登録できるようにする(Auth0 などの外部サービスのアカウントが要る)
  - 自前でパスワードを預かる
【決め手】 st.login は標準の機能で、一番早く安全。自前でパスワードを預かると、漏れたときの危険と、パスワード再設定の
          仕組みを作る手間が出る。
【決めた人】 提案をユーザーが了承した。
【変更履歴】 68

■ 7. ゲームの保存は手元ではファイル1つ(SQLite)、公開先ではクラウドのデータベース(2026-10-16〜17)
【決めたこと】 手元では SQLite(data/app.db)。公開するときは同じ関数のままクラウドのデータベースに替える。
【決め手】 手元で遊ぶうちはファイル1つで足りる。公開先(Streamlit Community Cloud)では、手元のファイルは再起動で
          消えることがあるので、購入の記録などを置くにはクラウドのデータベースが要る(公開時の選択は 05 を参照)。
【変更履歴】 68, 82
